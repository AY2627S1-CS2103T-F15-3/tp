Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts. For readability, the diagram omits StatusBarFooter and HelpWindow.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

Contact-card layout and expansion are described under Contact card layout.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

Logic component

API : Logic.java

Here's a (partial) class diagram of the Logic component:

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g., to delete a contact). A command that changes contact data also commits the change to the undo history.
  4. The command returns a CommandResult. LogicManager then saves the address book through Storage before returning that result to the UI.

For an example interaction trace, including batch-index validation, see Deleting one or more contacts.

Here are the other classes in Logic (omitted from the class diagram above) that are used for parsing a user command:

How the parsing works:

  • AddressBookParser#parseCommand dispatches on commandWord.toLowerCase(Locale.ROOT), so all command words are case-insensitive regardless of the system locale. Argument capitalization is retained. Whitespace is normalized before dispatch except for note, whose parser receives the raw arguments so that internal note whitespace can be preserved. Prefix matching and argument validation retain their existing rules, and Tag equality remains case-sensitive.
  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The Model component,

  • stores UniMate contact data i.e., all Person objects (which are contained in a UniquePersonList object). Each Person includes Major, GraduationYear and 'Notes' value objects in addition to its existing contact details and tags.
  • selects contacts using a FilteredList<Person> and orders that view using a SortedList<Person>. getFilteredPersonList() returns sortedPersons as an unmodifiable ObservableList<Person>, so the UI and numbered commands use the same displayed order. The filtered view takes its source from addressBook.getPersonList(), and the sorted view takes the filtered view as its source. Changes to the saved contact list therefore update the display.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • keeps an in-memory history of contact data states in an AddressBookHistory object. The undo and redo commands use it to revert and reapply every successful change to contact data. See Recording contact data history.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both UniMate contact data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

JsonUserPrefsStorage#readUserPrefs replaces explicitly null guiSettings with a default GuiSettings after deserialization. Missing settings already use the UserPrefs default; valid settings are preserved. This loading-boundary recovery keeps UserPrefs#setGuiSettings(null) invalid and prevents a null setting from reaching startup model initialization. Reading does not rewrite the file; the existing startup save persists the recovered defaults. Malformed JSON and null root values still follow the existing DataLoadingException recovery path.

FileUtil#writeToFile writes UTF-8 content to a sibling temporary file, closes the stream, then replaces the destination using ATOMIC_MOVE. It does not fall back to a direct overwrite when atomic replacement is unsupported. A failed write, close or replacement preserves the saved file and triggers temporary-file cleanup; cleanup failures are suppressed on the original exception. JsonAddressBookStorage no longer pre-creates an empty destination. FileUtilTest covers partial writes, replacement and cleanup failures, first saves, read-only files and symbolic links.

LogicManager keeps a snapshot of the initial contact data and updates it after each successful save. help returns its UI action without saving. exit also skips contact storage when the current contacts match that snapshot; otherwise, it retries saving and returns the exit flag only on success. A failed exit adds MESSAGE_UNSAVED_EXIT, so MainWindow keeps the window open with the pending contacts. list retains its save path for recovery. LogicManagerUiActionTest checks these state transitions, and StorageFailureUiTest submits Help and Exit through the actual command box.

JsonAdaptedPerson stores each contact's academic fields as the JSON properties major and graduationYear. Unspecified values are saved as empty strings. When loading older data files that omit either property, it treats the missing value as an empty string and constructs an unspecified Major or GraduationYear. Supplied non-empty values are validated before the contact is loaded.

JsonSerializableAddressBook#toModelType rejects null entries in persons, and JsonAdaptedPerson#toModelType rejects null entries in a contact's tag list, using IllegalValueException. JsonAdaptedTag also rejects a null tag name. JsonAddressBookStorage converts these validation errors to DataLoadingException, rejecting the whole file rather than returning a partial address book. Missing or null optional tag lists remain valid legacy data. Null-entry errors identify one-based positions in the saved persons and tags arrays, rather than GUI display indices. For example, Contact entry 2 is null. identifies a null contact, while Contact entry 2 is invalid: Tag entry 3 is null. identifies a null tag. Contact conversion errors include the contact position and retain the original validation exception as their cause.

JsonUtil#readJsonFile rejects a null JSON root as a DataLoadingException; it returns Optional.empty() only for a missing file. MainApp therefore uses its existing empty-contact-list fallback for invalid data, while missing files still use sample contacts. After a contact-loading error, StorageManager retains that failure and rejects contact saves with DataRecoveryRequiredException for the rest of its lifetime. This prevents list, changed commands and pending exit saves from replacing the rejected file. A subsequent successful read cannot unlock an old session whose model may still be empty; recovery requires repairing or restoring the file and restarting so the model is initialized from valid data. Preference saves remain available.

MainApp passes a recovery warning naming the file to UiManager; MainWindow shows it in amber before the first command. LogicManager handles a protected-save error separately from retryable write errors, explaining that any new changes are in memory and must be copied before closing. Help and an exit with no unsaved contacts still work. MainAppTest covers malformed JSON, invalid years, null entries and valid empty/missing files. StorageManagerTest checks protection after an external repair and recovery with a fresh storage instance; DataRecoveryUiTest checks the startup warning and command-box attempts to save over the rejected file.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Contact card layout

PersonListCard.fxml groups contact details and academic fields separately, with captions styled independently from their values in DarkTheme.css.

  • PersonCard populates values, tags and presence indicators. PersonListCell creates each card using its displayed index and binds its preferred width to the list width, reserving space for the scrollbar.
  • ExpandableText handles ellipses and click, Enter or Space expansion. PersonListPanel shares each contact's expanded-field state across recreated cells. This state is kept only in memory and does not change contact data or undo/redo history. The map uses value-equal Person objects as keys. A new contact state starts collapsed; an unchanged contact retains its state. Undo can reuse the entry for an earlier contact state and restore its expansion. Restarting the app clears the map.
  • ContactListNavigation filters Tab and Shift+Tab at the window root. It builds the route from the command box, list and selected cell's expandable values, skipping the result display and other cards. PersonCard supplies values in reading order; focusable tags are included. The route is rebuilt on each press because scrolling and resizing can recycle cells or change which values are shortened. The list skin's JavaFX VirtualFlow.scrollPixels brings focused values into view. Shift+Tab reverses the route. An empty list returns focus to the command box. Up/Down selection uses JavaFX's list behaviour; command-history keys and Enter/Space expansion keep their existing handlers.
  • PersonCardPane measures the card at its available width and stacks the detail groups below 560 logical pixels of content width. TagPane measures and places tag rows using the same wrapping calculation. Cell and card clips prevent content from painting over neighbouring cards.

PersonCardEdgeCaseTest covers all 128 combinations of optional fields and 12 long-value cases. PersonCardLayoutTest checks field captions and values at different widths. ExpandableContactListTest checks expansion, collapse, cell recycling, resizing and scrolling to the end of expanded content. ContactListNavigationTest checks forward/reverse traversal, selected-contact boundaries, arrow-key selection, empty lists and focused long-tag styling.

Contact notes

Structure and responsibilities

The class diagram shows how NoteCommand and Person reference Notes. Unrelated contact fields, parsers and history internals are omitted.

Notes is an immutable value object; Notes.EMPTY represents no note. Supplied text must be non-blank, on one line, free of control characters and at most 500 Unicode code points. Every Person holds exactly one non-null Notes value. The relationships are ordinary associations because values can be shared by contacts, commands and history snapshots.

Person#withNotes returns a replacement person with all other fields preserved, including favourite status and lastUpdated. Notes affect full equality and hashing, but not contact identity. Reusing the existing person-replacement mechanism keeps note changes compatible with undo/redo; edit, tag and untag also preserve notes.

JsonAdaptedPerson stores the text as notes and validates it when loading; missing or null values default to empty notes. PersonCard derives its orange noteIcon from getNotes().isEmpty() and updates when the observable list replaces a person. Its tooltip suggests shownote using the current displayed index; the icon itself is an indicator, while note text appears in command feedback.

Adding or replacing a note

AddressBookParser dispatches the three note commands to their parsers. NoteCommandParser treats everything after the index as literal text. It uses StringUtil.stripWhitespace before validation to trim Unicode whitespace, including non-breaking spaces that String.strip() misses. Internal whitespace is preserved. The other two parsers accept only an index.

The sequence shows execution after parsing; validation-error paths, feedback formatting and storage are omitted. m:Model is implemented by ModelManager and supplies the filtered, sorted displayed list.

  1. Resolve the displayed index and compare person.getNotes() with the supplied value. Identical notes return unchanged feedback before any snapshot, replacement or history commit.
  2. For a change, copy the address book, call person.withNotes(notes) and install the replacement with Model#setPerson, preserving the current filter and sort order.
  3. Commit the previous state once and return a CommandResult. New-note feedback includes the saved text; replacement feedback also includes the old text and an undo hint. The history description omits that hint so it remains appropriate in undo/redo messages.

LogicManager saves through Storage after successful execution, including unchanged-note results. Invalid input fails before mutation. Save errors leave the in-memory change and history intact; see history limitations.

The existing result display wraps and scrolls long feedback. At INFO level, LogicManager logs the command type and MainWindow logs CommandResult#getLogSummary, rather than raw input or full note text. This does not describe logging at other levels.

Parsing add prefixes

AddCommandParser passes the supported prefixes from CliSyntax to ArgumentTokenizer. Only those prefixes, preceded by a space, delimit fields. Unrecognised prefix-like text stays inside the preceding value and is validated as part of that field; it is not silently discarded or separately classified as an unknown parameter.

For example, add n/PrefixProbe a/NUS x/typo supplies NUS x/typo to ParserUtil.parseAddress. That address is valid and is saved literally. The same text inside a more restricted field may fail that field's validation. Slash-containing addresses remain valid unless a recognised prefix preceded by a space delimits a new argument. In add, f/ is now a recognised prefix, so a/Blockf/3 preserves the literal address without favouriting the contact, a/Block f/ supplies address Block and marks the contact as a favourite, and a/Block f/3 is rejected because the flag has a value. A space followed by f/ cannot represent literal address text in add. The UG warning and AddCommandParserTest document and cover these boundaries.

The optional f/ prefix is a flag with no value. AddCommandParser rejects values with the specific message The f/ flag does not take a value. Use f/ alone to mark the new contact as a favourite. and rejects repeated occurrences, then passes the flag's presence to the existing Person constructor as its initial favourite state. AddCommand saves this state in the same history snapshot as the new contact; no separate favourite command or history entry is needed. Its success message starts with New favourite contact added: for favourites and New person added: otherwise. The same message describes the addition in undo/redo history. After creation, fav and unfav change favourite status; edit preserves it. AddFavouriteIntegrationTest verifies these messages, saved data, favourites views, undo/redo, editing and rejected inputs, while FavouriteIconTest checks that the heart appears immediately after adding with the flag.

Adding academic fields

CliSyntax defines m/ for a major and c/ for a graduation year. AddCommandParser recognises these prefixes alongside the existing contact fields and rejects repeated occurrences of either academic prefix. Both fields are independently optional: an omitted prefix maps to Major.EMPTY or GraduationYear.EMPTY, whose empty string value represents an unspecified field.

For supplied values, ParserUtil.parseMajor and ParserUtil.parseGraduationYear trim leading and trailing whitespace and reject blank values. A major must contain non-whitespace text without control characters; spaces and punctuation are allowed. A graduation year must match 20[0-9]{2}, representing a four-digit year from 2000 to 2099. Invalid input produces a parse error before a contact is added.

The parser constructs a Person containing both academic values and passes it to AddCommand. The command checks for an existing contact with the same name, ignoring case, before adding the person to the model. Person#isSamePerson uses String#equalsIgnoreCase on Name.fullName, so the existing Model#hasPerson, UniquePersonList and edit duplicate checks share this rule. Name, Person#equals and Person#hashCode retain exact data equality, preserving capitalization changes for display, persistence and undo/redo. JsonSerializableAddressBook#toModelType also rejects case-only duplicate names using its existing IllegalValueException path. There is no automatic migration, deletion, merging or renaming. Users must back up legacy files and distinguish conflicting names before loading. The existing MainApp startup fallback opens an empty list with a recovery warning on a loading error, and StorageManager blocks contact saves for that session. Users must close UniMate, resolve conflicts in a copy of the backup, then reopen it before saving contacts; see data-file recovery. After a successful add, it records the previous contact data state in the model's history (see Recording contact data history). The normal storage path then saves the contact, including its academic fields.

Identifying an existing contact when add rejects a duplicate

AddCommand finds a saved contact using Person#isSamePerson and passes it to getDuplicateMessage. Messages#format reports that contact's actual details, rather than values from the rejected input.

Warning when an add introduces same contact details

After adding the contact, AddCommand#getAddResult calls SharedContactDetailsWarning#describeMatches on the refreshed full list. Sorting is retained, so warning indices match the current cards. Scanning after addition matters because a new contact can shift sorted positions.

The helper excludes the added contact and compares non-empty phone numbers exactly and emails ignoring case. It lists every match once, in displayed order, with the reason phone, email or phone and email. These advisory comparisons do not change contact identity or stored values.

SharedContactDetailsWarning#appendTo appends the matches to the complete success feedback and returns a CommandResult.warning. Add and edit share this helper to keep formatting consistent. MainWindow passes the result's warning flag to ResultDisplay; the warning style in DarkTheme.css makes the whole message amber. The existing text area handles wrapping, selection and scrolling. The next ordinary result restores normal styling, and getLogSummary() excludes the appended matches.

The addition remains successful and is saved normally. The history description contains only the ordinary addition message: one undo removes the new contact, and redo restores it without repeating the advisory. Existing contacts are not modified or merged.

Editing academic fields

EditCommandParser recognises m/ (major) and c/ (graduation year) alongside existing edit prefixes. It rejects repeated academic prefixes and validates supplied values using ParserUtil.parseMajor and ParserUtil.parseGraduationYear. An empty prefix value maps to Major.EMPTY or GraduationYear.EMPTY to clear the optional field; an omitted prefix leaves the descriptor field null.

EditCommand.EditPersonDescriptor stores, copies and compares both academic fields. EditCommand uses the supplied values when constructing the edited Person, retaining existing values for omitted fields. The existing model update and JSON storage path save the edited values without a storage format change. After a successful edit that changes the contact, EditCommand records the previous contact data state in the model's history (see Recording contact data history).

Searching by academic fields

Parsing

FindCommandParser trims user input and splits it on whitespace into keywords. Input passed on to PersonContainsKeywordsPredicate.

Blank input throws a ParseException with FindCommand.MESSAGE_USAGE.

Prefixes are not tokenized, so find n/Alex searches for the literal word n/Alex.

Matching

The predicate matches a Person if any keyword matches a full word in the person's Name, Major or GraduationYear, using StringUtil.containsWordIgnoreCase.

  1. Matching is case-insensitive, whole-word and OR-based across all three fields. Partial words do not match. (Note: exact matching on a whole field value is provided by filter instead)

    • find Comp does not match Computer Science
    • find Computer Science can return any contact whose major is Data Science

  2. Field values are split on whitespace, so punctuation stays attached to a word:

    • find Hons does not match Computer Science (Hons), but find (Hons) does

  3. Names are alphanumeric, this affects majors only.

  4. An empty Major or GraduationYear never matches a keyword.

  5. Not specified placeholder is added only for display and is not stored.

  6. AddressBookParser converts Unicode spaces in the arguments to ASCII spaces before FindCommandParser runs, so every keyword passed to containsWordIgnoreCase is a single word.

Updating the displayed list

FindCommand applies the predicate through Model#updateFilteredPersonList. filter reuses this path unchanged.

  1. The new predicate replaces the previous one, so every find searches all saved contacts, not just the displayed ones.

    • find replaces any filter or listfav view
    • list, add, edit, undo and redo show all contacts again; the view is not saved, so a restart also shows all contacts

  2. The SortedList comparator is untouched, so an active sort is kept.

  3. The predicate implements PersonFilter, so its description appears in the view status.

    • find alex david shows Filter: Search: alex OR david

  4. find changes no contact data and never calls Model#commitAddressBook, so undo and redo availability is preserved.

  5. The model and storage format are unchanged.

Filtering contacts by academic fields and tags

filter updates the displayed list in the same way as find: FilterCommand passes its predicate to Model#updateFilteredPersonList and reports the number of shown contacts. It also replaces the previous view, keeps the active sort and records no history. This section covers only how filter differs.

Parsing

FilterCommandParser tokenizes only m/, c/ and t/ as criterion delimiters, then rejects a non-empty preamble, missing criteria and repeated prefixes. Other prefix-like text stays within the preceding value: m/Mathematics w/ Computing represents the complete major Mathematics w/ Computing, as in add and edit. Each supplied value is validated with ParserUtil.parseMajor, parseGraduationYear or parseTag; a blank supplied value is invalid. An omitted criterion becomes an empty Optional and is ignored by ContactFilterPredicate#test. Unknown text before the first criterion is a usage error; unknown text within a year or tag fails that field's validation. Recognised criterion prefixes remain reserved syntax.

Interaction with tag commands

Unlike find, the predicate depends on tags. tag and untag keep the current predicate, so a contact disappears from the results when its tags no longer match.

Sorting the displayed contacts

AddressBookParser routes sort to SortCommandParser. The parser accepts either two tokens (a field name, major, year or updated, followed by asc or desc) or the single keyword reset. Keywords are case-insensitive. A field and direction produce SortCommand with PersonSortComparator.SortField and SortDirection values; reset produces SortResetCommand. Invalid input raises a ParseException with usage instructions before any view or data change.

The sequence below traces sort year desc from parsing to the Model sorting API. It shows how the command supplies a comparator; list transformations and comparison rules are explained below.

SortCommand#execute supplies a PersonSortComparator to Model#updateSortedPersonList. ModelManager maintains this observable transformation chain:

AddressBook / UniquePersonList -> FilteredList -> SortedList -> UI and numbered commands

getFilteredPersonList() retains its existing API name and now returns the sorted view. Consequently, edit, delete, tag and untag obtain the same indexed Person that is shown on the matching contact card. The SortedList object is retained for the model's lifetime, keeping existing UI observers attached. Changing its comparator preserves the FilteredList predicate; changing the predicate preserves sorting. SortResetCommand calls Model#resetSortedPersonList, which sets the comparator to null. The same displayed list then follows source order without changing the predicate, saved data or history.

The comparator uses case-insensitive full-value ordering for names and majors. Graduation years are four-digit strings, so their lexicographic order is chronological. Empty academic values become null sorting keys. Direction is applied to the value comparator before Comparator.nullsLast, ensuring that descending order does not move unspecified values to the front. Equal primary values use ascending case-insensitive name order; names differing only in case compare equally.

For UPDATED, the comparator compares Person#getLastUpdated() as LocalDate values. Ascending puts older dates first; descending reverses only the date comparison, keeping the ascending name tie-break in both directions. Missing/null dates in older files remain unknown and sort last in both directions using Comparator.nullsLast; unknown-date ties use ascending names. The view status describes this field as Last updated. Replacing a contact after an edit or restoring it through undo/redo automatically reorders the displayed view using the restored date.

Sorting the view rather than UniquePersonList preserves storage order and history snapshots. As with other successful commands, LogicManager still invokes storage, but the saved contacts remain in their underlying order. Sort commands do not call commitAddressBook, so undo and redo availability is preserved. Add/edit/undo/redo retain their existing behaviour of clearing the filter, while keeping the comparator. Replacing, adding or removing source contacts automatically updates their sorted positions. Restarting constructs a view without a comparator or predicate, restoring saved order and all contacts.

Deleting one or more contacts

The sequence shows successful batch deletion after parsing. Resolve every target before mutation, then commit once; parsing, validation-error branches and storage are omitted.

  1. DeleteCommandParser splits whitespace-separated arguments and validates positive integers with ParserUtil#parseIndex. DeleteCommand stores the indices in input order.
  2. The command copies Model#getFilteredPersonList(), checks every selection and captures the target Person references. Numeric duplicate detection also rejects equivalent indices such as 1 01.
  3. After validation, it copies the address book once and calls Model#deletePerson for each captured person. Resolving all targets first prevents shifting live indices from selecting the wrong contact.
  4. It formats the result with Messages#format, calls commitAddressBook(previousState, message) once and returns a CommandResult. LogicManager then saves the completed batch once.

An invalid or repeated index rejects the whole batch before mutation, preserving contacts, view and history. Out-of-range errors include the valid range; an empty view suggests list if saved contacts exist, or adding a contact otherwise.

Deletion removes each selected person and all their saved fields, including notes. Single-contact feedback starts with Deleted person:; batch feedback includes each original index in input order. The result also serves as the history description. One undo/redo reverses/reapplies the batch and shows the full list; deletion itself preserves the filter, sort order and all unselected contacts.

This design extends the existing single-contact operation without introducing separate batch-history state. DeleteCommandIntegrationTest checks selection, rejection, persistence and one-step undo/redo; SortUiTest checks feedback and card renumbering. See Deleting contacts for manual tests.

Tracking and displaying contact update dates

Person#getLastUpdated() exposes an immutable LocalDate representing creation or the most recent actual change to the basic profile: name, phone, email, address, major and graduation year. Tags, notes and favourite status retain the original date. Date values participate in full equality, hashing and history snapshots, but do not affect name-based contact identity.

Assigning and preserving the date

AddCommand obtains LocalDate.now(clock) during successful execution, rather than relying on the date from when its Person was constructed. Person#withLastUpdated creates a dated copy preserving all other fields. This handles a command prepared before midnight but executed afterwards. The default clock uses the computer's time zone; tests can supply a fixed clock. Duplicate detection still occurs before mutation or history recording.

EditCommand#createEditedPerson compares the resulting six basic fields with the original values. An actual change, including clearing a specified optional field, refreshes the date using its clock. An unchanged edit or tag-only edit retains the previous date. Failed parsing, an invalid index and duplicate-name rejection leave the stored contact unchanged. Undo and redo restore the recorded date, rather than calculating a new date when restoring a snapshot.

For example, a contact starts with date 2024-02-29. Submitting its existing phone or changing only a tag keeps that date. A subsequent phone change on 2026-10-28 records 2026-10-28. Undoing the phone change restores 2024-02-29, and redoing it restores 2026-10-28, even if redo runs on a later day.

Display and JSON compatibility

PersonCard sets the always-visible lastUpdated label from Person#getLastUpdated() in PersonListCard.fxml, producing Last updated: YYYY-MM-DD for ordinary four-digit years or Last updated: Unknown when no date was recorded. Its tooltip explains the scope of the date. Replacing a person updates the observable list cell, so edits, undo/redo and reloaded data all display the corresponding date. The label is independent of the derived update reminder and appears on recent contacts too.

The existing JSON lastUpdated string and LocalDate.parse validation are reused. Missing/null dates remain unknown and are saved as JSON null until an actual basic-profile edit records a date. Invalid supplied dates fail data loading. No new JSON property or user-supplied date prefix is introduced.

Design considerations and verification

Storing the date on the immutable Person keeps it with contact data through persistence and history restoration. Calculating it only for actual basic-field changes prevents a note, favourite or repeated edit from making old profile information appear current. LocalDate matches the day-level display; it does not provide a time of day or an interaction history. Preserving an unknown legacy date avoids inventing an update when an older contact is loaded.

Reminder logic

  • Exactly one year produces no reminder.

  • Tag order is not guaranteed. Equality remains case-sensitive, so NOC and noc are distinct.

Aspect: Compatibility with existing editing

Recording contact data history

Current implementation

The model keeps an in-memory history of contact data. The user-facing undo and redo commands are built on this history (see Undo and redo commands).

  1. Every command that changes contact data records the state from before its change.

  2. The model can restore earlier or later states.

  3. The history lasts only for the current session.

    • it is not saved to storage
    • a newly launched app starts with no undo or redo history

Class Responsibility

History state

AddressBookHistory holds:

  • undoStates: the contact data from before each recorded change, most recent on top.
  • redoStates: the contact data that has been undone, most recent on top.
  • currentState: a copy of the contact data in the tracked AddressBook.

  1. Each entry in either stack is a private Change record holding a snapshot and a short description of the change between it and the adjacent state.

    • e.g. Tagged person: …​

  2. getUndoDescription() and getRedoDescription() return the description at the top of the corresponding stack.

    • they return an empty Optional if there is no valid state to restore

  3. Every stored state is a copy made with new AddressBook(...).

    • Person and its fields are immutable, so later changes to the model cannot alter a stored snapshot

Execution flow

Committing a change

Below is the flow for a successful add n/Alex Tan …​:

  1. AddCommand#execute searches the saved person list using Person#isSamePerson.
    • If the resulting Optional<Person> contains a duplicate, it throws a CommandException, nothing is recorded.
  2. The command creates previousState = new AddressBook(model.getAddressBook()), then calls Model#addPerson.
  3. The command formats its success message and calls Model#commitAddressBook(previousState, message).
    • AddressBookHistory#commit then:
      • returns without recording if previousState holds the same contacts as the current data;
      • clears undoStates if previousState differs from currentState, which means an unrecorded change happened earlier (see below);
      • pushes a copy of previousState with message onto undoStates, clears redoStates, and sets currentState to a copy of the current data.
  4. The command returns the same message as its CommandResult. LogicManager saves the contact data to storage as before. History itself is not saved.

A command that fails validation, such as a duplicate add, throws before copying the data and never reaches this flow.

Other data-changing commands

Every other command that changes contact data follows the same snapshot-and-commit pattern.

  1. EditCommand#execute checks the displayed index and duplicate persons first, copies the data, calls Model#setPerson, and then commits.

    • an edit that supplies the person's current values returns the no-change message before snapshotting or committing, so both history stacks and the existing update date are preserved
    • edit 1 is invalid because at least one field is required

  2. NoteCommand and DeleteNoteCommand commit only actual note changes.

    • NoteCommand returns immediately for unchanged note text, without copying the address book, replacing the contact or committing history, so redo remains available
    • DeleteNoteCommand returns immediately for an empty note
    • viewing a note does not clear redo states

  3. DeleteCommand, ClearCommand, TagCommand, UntagCommand, FavCommand and UnfavCommand copy the data after their validation checks, make the change through Model#deletePerson, Model#setAddressBook or Model#setPerson, and then commit.

  4. Changes that leave the data unchanged are ignored by the commit, so no undo step is recorded and redo remains available.

    • tag with a tag the person already has
    • untag with a tag the person does not have
    • clear on an empty contact list

  5. fav on a person who is already a favourite and unfav on one who is not fail before copying the data.

  6. A DeleteCommand with multiple indices captures all target contacts before mutation and commits only after every selected contact has been deleted.

    • the whole batch consumes one undo step, with its feedback stored as the history description
    • invalid or repeated indices preserve both history stacks
Restoring a state

Model#undoAddressBook() and Model#redoAddressBook() move one entry between the stacks.

  1. Model#undoAddressBook() pops the top of undoStates, pushes currentState onto redoStates with the popped entry's description, and restores the popped state. Model#redoAddressBook() does the reverse.

    • the description moves with its change between the stacks, so a redo names the same change that the matching undo named

  2. Restoring calls AddressBook#resetData on the existing AddressBook.

    • the AddressBook object and the FilteredList built on it are the same objects before and after, and the UI updates through its existing observers
    • restoring a state does not record a new history entry

  3. Both methods return true if a state was restored.

    • they return false and leave the data unchanged if there is nothing to restore

Example usage scenario

The diagrams below show how the history changes as a user enters a sequence of commands. Each abN is an AddressBook snapshot, and each stack is drawn with its top entry first.

Step 1. The user launches a disposable, empty address book.

currentState is a copy of its contacts, ab0, and both stacks are empty. The example uses a name that is not already saved.

Step 2. The user runs the following commands in order: add n/Alex Tan a/NUS find Alex Tan edit 1 p/91234567

The add and edit commands commit the state from before their changes: add pushes ab0 onto undoStates and currentState becomes ab1; edit then pushes ab1 and currentState becomes ab2. The intervening find changes only the view and records no history entry.

Step 3. The user runs undo.

ab2 is pushed onto redoStates, and ab1 is popped from undoStates and restored.

Step 4. The user runs redo.

This reverses Step 3: ab1 is pushed back onto undoStates, and ab2 is popped from redoStates and restored. The history is again as shown after Step 2.

Step 5. The user runs undo again, then runs add n/Beth Lim …​.

This pushes ab1 and clears redoStates, so the undone edit, ab2, can no longer be redone. currentState becomes ab3.

Commands that do not change contact data, such as list and find, and commands that fail before changing anything, record nothing and leave all three parts of the history unchanged.

Unrecorded changes

Every current command that changes contact data commits its change.

A future command that changes the data but forgets to call Model#commitAddressBook would be dangerous: restoring an old snapshot after it would silently reverse that change as well.

  • e.g. if such a command removed a contact after an add, undoing the add would also bring back the removed contact

As a safety net, AddressBookHistory compares currentState with the live contact data. If they differ, a change was made without being recorded, and the history is stale:

  1. canUndoAddressBook() and canRedoAddressBook() return false.

  2. undoAddressBook() and redoAddressBook() discard both stacks and return false, leaving the data unchanged.

  3. The next data-changing commit discards the stale undo states before recording the new one.

Continuing the example above, suppose an unrecorded change now replaces the contacts in the model with ab4, so they no longer match currentState, ab3.

  • the history is now stale
  • a following user undo command is rejected with There is no change to undo., rather than restoring ab1 and reversing the unrecorded change; UndoCommand checks canUndoAddressBook() first, so it does not call undoAddressBook() and the stale stacks are left in place
  • the stale stacks are only discarded when undoAddressBook() or redoAddressBook() is called directly on the model, or by the next data-changing commit

To the user, such a change only makes undo and redo report that there is nothing to undo or redo, never restore the wrong data. UndoCommandTest covers this by changing the model directly without committing.

Known limitations

The history has no size limit, and a failed save does not roll back the change. Both are described in Appendix: Known limitations.

Design considerations

Aspect: What is stored for each change

  • Alternative 1 (current choice): Store a copy of the whole contact data state.
    • Pros: Easy to implement and to verify, and works the same for any command.
    • Cons: Uses more memory as the number of contacts and history entries grows. The history is not trimmed (see Known limitations).
  • Alternative 2: Each command stores how to reverse itself (e.g. add stores the person to remove).
    • Pros: Uses less memory.
    • Cons: Every command needs its own correct reversal logic.

Aspect: How the history is structured

  • Alternative 1 (current choice): An undo stack and a redo stack in a separate AddressBookHistory class.
    • Pros: Clearing redo history is a single clear() call. AddressBook stays unchanged, and history can be tested on its own.
    • Cons: ModelManager has to hold and delegate to another object.
  • Alternative 2: A VersionedAddressBook subclass with a list of states and a current-state pointer.
    • Pros: Keeps history and data in one object.
    • Cons: Discarding redo states requires trimming the list after the pointer, and AddressBook gains history responsibilities.

Aspect: Which commands are undoable

  • Alternative 1 (current choice): Every command that changes contact data commits its change.
    • Pros: Users can rely on one rule: any change can be undone, including delete and clear, where mistakes are most costly. Each command needs only a snapshot and a commit call.
    • Cons: A full snapshot is stored for every change, including small ones such as fav.
  • Alternative 2: Only some commands, such as add and edit, are undoable; the others make earlier history unavailable.
    • Pros: Fewer snapshots are stored.
    • Cons: Users must remember which commands can be undone, and a non-undoable command also blocks undoing earlier changes. This was the earlier behaviour, and it was reported as confusing for fav and unfav.

Aspect: How unrecorded changes affect history

  • Alternative 1 (current choice): Detect unrecorded changes by comparing the expected state with the live data.
    • Pros: A future command that forgets to commit cannot cause an old snapshot to silently reverse its change.
    • Cons: Each history check compares the whole contact list. If an unrecorded change is later reversed exactly, the history becomes valid again, which is safe because the data is identical.
  • Alternative 2: Trust every data-changing command to commit, with no check.
    • Pros: Avoids the comparison on every history check.
    • Cons: A single missing commit would let undo restore the wrong data, and the model alone cannot detect it because many commands share Model#setPerson.

Undo and redo commands

Current implementation

The undo and redo commands let users revert and reapply any change to contact data using the history described in Recording contact data history.

Relevant classes
Class Responsibility
AddressBookParser Recognises the undo and redo command words. Throws a ParseException with MESSAGE_INVALID_COMMAND_FORMAT and the command's usage if any arguments follow the command word.
UndoCommand Checks Model#canUndoAddressBook(), reads Model#getUndoDescription(), calls Model#undoAddressBook(), and shows all contacts.
RedoCommand Checks Model#canRedoAddressBook(), reads Model#getRedoDescription(), calls Model#redoAddressBook(), and shows all contacts.

Neither command has its own parser class, because neither takes any arguments.

Execution flow

Undo flow

Given below is the flow for undo:

  1. LogicManager#execute passes the input to AddressBookParser#parseCommand. If anything follows the command word, such as in undo 1, a ParseException is thrown and the model is never reached.
  2. The parser returns a new UndoCommand, and LogicManager calls UndoCommand#execute(model).
  3. The command checks Model#canUndoAddressBook(). If it returns false, the command throws a CommandException with UndoCommand.MESSAGE_FAILURE. The exception propagates out of LogicManager#execute before the save step, so neither the data nor the data file changes.
  4. Otherwise, the command reads the description of the change about to be reversed with Model#getUndoDescription(), then calls Model#undoAddressBook(), which restores the previous state in place. It then calls Model#updateFilteredPersonList(PREDICATE_SHOW_ALL_PERSONS) so that every restored contact is visible, even if a find, filter or listfav view was active, and returns a CommandResult with UndoCommand.MESSAGE_SUCCESS formatted with that description.
  5. LogicManager saves the restored contact data through Storage#saveAddressBook, as it does for other contact-data commands.

The sequence diagram below shows steps 1 to 4 for execute("undo"), including the failure path when there is nothing to undo. The save to storage in step 5 is omitted.

Redo flow

redo follows the same flow using RedoCommand, Model#canRedoAddressBook(), Model#getRedoDescription() and Model#redoAddressBook().

  1. Neither command calls Model#commitAddressBook.

  2. Restoring a state moves it between the undo and redo stacks without adding a new entry.

    • repeated undo keeps moving back through earlier states
    • redo does not clear the remaining redo states
Save failures

  1. If saving fails after a successful undo or redo, the in-memory state has already been restored.

  2. LogicManager reports the file error, as it does for other commands.

  3. The history remains consistent with the in-memory data.

Design considerations

Aspect: Where the availability check happens

  • Alternative 1 (current choice): The command checks canUndoAddressBook() or canRedoAddressBook() first and throws a CommandException if it returns false.
    • Pros: The failure is reported through the usual command error path. The boolean returned by undoAddressBook() and redoAddressBook() only acts as a safety net.
    • Cons: The command makes an extra availability-check call before restoring history.
  • Alternative 2: Call undoAddressBook() or redoAddressBook() directly and use the returned boolean to choose the message.
    • Pros: No separate availability-check call. Description lookup and view reset are still needed.
    • Cons: The command's decision depends on the result of a call that may also discard stale history as a side effect, which is harder to follow.

Aspect: How the undone or redone change is described

  • Alternative 1 (current choice): Each command passes its history description (edit uses full contact details rather than its immediate change summary) to commitAddressBook, and the history stores it with the snapshot.
    • Pros: Most commands reuse their success message without new wording. Edit retains its established full-contact description so undo/redo identifies the affected contact without repeating field or tag differences.
    • Cons: Messages that include a full Messages#format of the person are long. Each command must remember to pass a description, although the two-argument signature makes it impossible to commit without one.
  • Alternative 2: Work out the description by comparing the two snapshots, e.g. finding the contact that was added or removed.
    • Pros: Commands need no change.
    • Cons: The comparison cannot tell a tag from an edit that only changes tags, and it needs separate logic for every kind of change.

Aspect: Handling extra arguments

  • Alternative 1 (current choice): Reject input such as undo 1 with a parse error.
    • Pros: Users are not misled into thinking undo 3 undoes three changes or a specific contact, and no history changes by accident.
    • Cons: Inconsistent with help, exit and clear, which ignore extra parameters.
  • Alternative 2: Ignore extra parameters, as help does.
    • Pros: Consistent with the other commands that take no parameters.
    • Cons: undo 3 would silently undo only one change.

Aspect: What is displayed after restoring

  • Alternative 1 (current choice): Show all contacts after every undo or redo.
    • Pros: The restored or removed contact is always visible, and indices from an earlier filtered list are not reused by mistake.
    • Cons: The user loses the current find filter.
  • Alternative 2: Keep the current filter.
    • Pros: The user keeps their search context.
    • Cons: The restored change may be hidden by the filter, so it can look as if nothing happened.

Command history navigation

These activities separate older-command recall from newer-command recall and draft restoration. Prefix matching keeps the initial prefix until editing or chronological navigation resets it.

CommandBox owns a session-local CommandHistory. A KEY_PRESSED event filter on its text field consumes Up/Down events, recalls the corresponding text and moves the caret to its end. When recalled text differs from the current input, the existing text listener clears the error style. Recalling an identical string does not trigger that listener. Browsing does not execute a command or change the result display or contact list.

CommandHistory stores submissions in order, including duplicates and failed commands. CommandBox records non-empty input before calling the executor, so parse and execution errors remain recallable. Each submission resets the navigation position to the end. On the first Up from the end, history saves the current draft; Down past the newest entry restores it. Navigation stops at the oldest entry, and Down at the draft position leaves input unchanged. Editing recalled input does not change stored entries. History is held in memory and is not written to contact data or preferences.

Alt+Up/Down (Option+Up/Down on macOS) calls previousMatching / nextMatching on the same history cursor. previousMatching captures the current input as a case-sensitive startsWith prefix; subsequent searches retain it, skipping unrelated entries. No older match leaves the cursor unchanged. After the newest match, nextMatching restores the saved draft and ends the search. Without an active search, Alt+Down is a no-op. Editing input, submitting a command or using chronological arrows resets the prefix. CommandBox guards programmatic recalls so its text listener resets the search only for external edits. Switching navigation modes keeps the original draft and the current history position.

Internally, position is zero-based in 0..commands.size(), inclusive; the upper bound denotes the draft rather than a stored command. The GUI converts stored positions to one-based labels; a no-match search preserves the cursor and therefore the label. Both activity diagrams include the label update, even when no text changes or a shortcut leaves the search inactive.

CommandHistory#getPosition() exposes a one-based chronological index (zero at the draft), and size() includes all submissions, even duplicates. After each navigation event, CommandBox updates the adjacent historyPositionLabel to History i/N. A 200 ms FadeTransition restarts from 35% to full opacity on each press, including boundary presses and identical recalls. At the draft and on Enter, the transition stops and the label becomes invisible and unmanaged so the input reclaims its space. Failed submissions also hide the label. Prefix search displays absolute positions rather than match counts. This recall history stores command strings independently of AddressBookHistory: recalling a failed command is valid even though that command created no contact-data undo entry.

CommandHistoryTest covers boundaries, duplicates, exact prefixes, mode switching and draft state. CommandBoxTest exercises the real FXML text field on the JavaFX thread: Up/Down event consumption, caret placement, draft restoration, failed submissions, error styling, Alt shortcuts, edited prefixes and the absence of executor calls during browsing. For manual UI verification:

  1. Submit list, then an invalid command. Press Up twice and verify both can be recalled in reverse order.
  2. Press Up again at the oldest entry; verify it stays displayed. Press Down to return to the newest entry.
  3. Return to the draft position, type a partial command, then press Up and Down; verify the draft is restored.
  4. Edit a recalled command and submit it; verify the new submission is the newest entry.
  5. Submit add n/Alice a/NUS, list, add n/Bob a/NUS, then list. Type add and use Alt+Up twice: verify Bob then Alice is recalled, skipping List entries. Alt+Down twice restores Bob then add .
  6. Verify no matches leave input unchanged, and ordinary arrows still visit all entries after prefix search.
  7. Submit list three times. Press Up repeatedly and verify the label shows distinct absolute positions, pulses even at the oldest entry, then disappears when Down restores the draft or Enter submits input.
  8. Restart UniMate and verify both navigation modes leave the input unchanged until a command is submitted.

  7. Invalid command input should produce a meaningful error without crashing.

Operating constraints

UniMate supports only one running instance at a time. Concurrent use by multiple instances is unsupported, and behaviour in that situation is undefined. Users are informed of this restriction in the Quick start.

Glossary

  • Category: A grouping used to organise contacts by a shared attribute or context, such as a module, major, CCA, event, or project.
  • CCA (Co-Curricular Activity): An organised student activity outside academic classes, such as a sports club, performing arts group, or student society.
  • CLI (Command-Line Interface): An interface in which users type text commands to perform operations. UniMate accepts these commands through the command box in its graphical window.
  • Contact: A record representing a person in the user's collection, containing their name and contact information. Also referred to as a person in this guide.
  • Contact information: Details recorded about a person, such as their phone number, email address, and postal address.
  • Contact list index: The one-based position of a contact in the currently displayed list, used by commands to select that contact. It is not a permanent identifier for the person.
  • Graduation year / Class year: The calendar year in which a person graduates or expects to graduate, such as 2027 (class of 2027). This differs from their current year of study. UniMate accepts years from 2000 to 2099.
  • GUI (Graphical User Interface): An interface that presents information through visual elements such as windows, lists, and buttons.
  • Major: A student's principal academic field of study, such as Computer Science.
  • Module: A university course or unit of study, typically identified by a code such as CS2103T. Here, it refers to an academic course rather than a software component.
  • Private contact detail: A contact detail that is not meant to be shared with others.
  • Tag: A text label attached to a contact to help organise the contact collection. A contact can have multiple tags.
  • Tutorial group: A group of students assigned to attend the same tutorial session for a particular module.
  • University-related context: Information that connects a contact to university life, such as their module, major, year of study, CCA, or the event or project through which the user knows them.
  • Year of study: A student's current stage in their university programme, such as Year 1 or Year 2, rather than a calendar year.

PermCheck appears in the list.
  4. Close the app and open data/unimate.json in a text editor. Expected: It does not contain PermCheck.

Testing save-failure recovery

Use only a disposable copy with a valid backup; this scenario intentionally blocks writing.

  1. Launch normally and run list once to create data/unimate.json. Keep UniMate open. Move that file to a safe backup filename and create an empty directory named unimate.json at its former path. This blocks saving without relying on OS-specific permission commands.
  2. Run add n/SaveFailureCheck a/NUS. Expected: A save error replaces success feedback, but the contact appears in memory. The error explains that the change is unsaved and that undo can revert it. The command text remains for correction.
  3. Replace the input with undo, then redo, while the directory still blocks saving. Expected: Undo removes the contact in memory, restoring the saved state, so its save error has no unsaved-change note. Redo restores the contact in memory and reports another save error naming undo as the reversal. No successful save has occurred.
  4. Remove only the empty blocking directory and restore the backed-up file to its original path. Run list, then restart and run find SaveFailureCheck. Expected: list saves the current in-memory contacts successfully. The newly added contact is present after restart. Retain the original backup until the whole scenario is finished.

For startup loading failures, use the separate saving-data scenarios: close the window without commands before repairing a malformed file. That is different from this deliberately blocked save while a valid session is already running.

Appendix: Planned enhancements

Team size: 6

Each item below is a planned fix for a limitation listed in Appendix: Known limitations.

  1. Make email validation stack-safe for extremely long input. Email.VALIDATION_REGEX uses nested repeated groups such as ([+_.-][^\W_]+)*. Java's regex engine matches these recursively, so an email with thousands of repeated segments (e.g., "a." repeated 5,000 times followed by a@example.com) throws StackOverflowError. The exact threshold depends on the thread stack size and JVM, so no fixed limit is documented. Such a value can be accepted when added in the UI and saved, but the same check then fails while JsonAdaptedPerson#toModelType loads the file, so the next launch terminates in MainApp#init. The input is far outside any real email address, so this is a robustness limitation rather than a normal-use failure. Planned fix: replace the repeated-group regex with an iterative check that splits the local part and domain on their separators and validates each segment, and add a test that saves an accepted long email, then launches the app in a fresh JVM against that saved file and checks that startup succeeds. A reload through another storage object in the same JVM is not enough, because the overflow depends on the thread stack and the real failure occurs in MainApp#init. Catching StackOverflowError alone is not planned, as it would hide the design problem.

  2. Check the final domain label's length separately from its syntax. DOMAIN_LAST_PART_REGEX is (label){2,}$, which requires the label pattern to repeat at least twice, not the final label to have at least two characters. As a result, a@x.y-z and a@a-b are rejected although they satisfy the stated rules, while a@ab-c and a@a-bc are accepted. The command is rejected cleanly without changing data. The User Guide currently states the narrower accepted rule. Planned fix: match the final label with the ordinary label pattern and check its length with a separate condition, so the validator matches Email.MESSAGE_CONSTRAINTS.

  3. Report, instead of silently removing, control characters in pasted input. Notes rejects tabs and line breaks, but the command box is a single-line JavaFX TextField, which strips them from pasted text before CommandBox#handleCommandEntered runs. Pasting Left<TAB>Right into note 1 ... therefore saves LeftRight. The parser-level rejection still applies to text that reaches it by other routes. The User Guide documents the stripping. Planned fix: add a TextFormatter to the command box that replaces pasted tabs and line breaks with spaces, so words stay separated and the user can see the result before pressing Enter.

  4. Show a focus outline on the message area. Ctrl+Tab moves focus to the ResultDisplay text area, but nothing on screen shows it. The .result-display rule in DarkTheme.css replaces the text area's background with one flat colour and zero insets, and JavaFX draws a text area's focus ring as part of that background. This falls short of the requirement that focus remain visible (non-functional requirement 3). Keyboard scrolling and Ctrl+Shift+Tab still work, and the User Guide explains how to check focus. Planned fix: add a .result-display:focused rule that draws a border in the existing -fx-focus-color (orange), matching the outline used for expandable contact values.

Other limitations

  1. The history has no size limit.

    • every recorded change stores a full copy of the contact list, with no automatic cap or eviction of the oldest snapshots
    • undo and redo still move entries between the stacks, and a new change clears the redo branch
    • memory use grows with the number of contacts times the number of changes in a session
    • this is acceptable for the expected size of a student's contact list; a future version could cap the number of entries and drop the oldest snapshot when the cap is reached

  2. A failed save does not roll back the change.

    • contact-data commands commit to history before LogicManager#execute saves to storage; an IOException becomes a saving-related CommandException
    • the in-memory change and history remain, while the saved file is protected by the temporary-file replacement described under Storage
    • LogicManager compares the current immutable person list with its initial state or last successful save to identify pending changes
    • a failed changed command gets MESSAGE_UNSAVED_CHANGE, naming redo after undo and undo otherwise; a failed retry such as list gets MESSAGE_PENDING_UNSAVED_CHANGES when earlier changes still need saving
    • returning to the saved state through undo clears the pending-change condition, so no unsaved-change note is added in that case
    • list retries saving all current contacts; Help remains available, while Exit retries pending saves and stays open if they still fail
    • the user guide documents this under Saving the data

  3. Ctrl+Tab into the message area is not implemented by UniMate.

    • ContactListNavigation#handleTab consumes only plain Tab and Shift+Tab. It returns early when Ctrl, Alt or Meta is held, leaving Ctrl+Tab to JavaFX's default focus traversal.
    • JavaFX binds Ctrl+Tab and Ctrl+Shift+Tab to "next/previous control", because a text area normally keeps plain Tab for typing.
    • The default order follows MainWindow.fxml: command box, then ResultDisplay, then the contact list. ResultDisplay's TextArea is focus-traversable by default, so Ctrl+Tab from the command box reaches it.
    • The route is fragile: reordering the layout, making the text area non-traversable or consuming Ctrl+Tab in handleTab would remove it silently. No automated test covers it.
    • A future version could handle Ctrl+Tab explicitly in ContactListNavigation and add a GUI test for the command box → message area → command box route.

  4. Long search or filter criteria can hide the contact list.

    • PersonListPanel.fxml gives the wrapping viewStatus label its full preferred height without a maximum. Its text can push the ListView below the visible window.
    • Reproduced on Windows at 450 × 600: add StatusProbe, then run find StatusProbe followed by 250 space-separated a keywords. The search finds the contact, but the list is no longer visible. A long exact-major filter has the same effect.
    • Run list to clear the criteria and restore the list, then use a shorter query. Contact data is unchanged by the search or filter.

  5. Tab can skip an off-screen selected contact.

    • ContactListNavigation#getFocusRoute searches currently loaded PersonListCell nodes. If scrolling has recycled the selected card, its expandable values are absent from the route.
    • Reproduce with enough contacts to scroll: select a contact with an expandable value, keep the list focused, scroll until that card is out of view, then press Tab. Focus returns to the command box instead of an expandable value.
    • From the command box, press Tab to scroll the selected contact back into view and focus the list, then Tab again to reach its first expandable value. handleTab scrolls to the selection when focus starts in the command box.
    • Both UI workarounds are documented in the UG known issues and were rechecked on Windows.

  6. Untested requirements.

    • The one-second response target with 1,000 contacts (non-functional requirement 2) has not been measured end to end, including UI rendering.
